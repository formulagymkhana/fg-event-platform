# GAS コード同期に clasp を導入する手順（2026-08-17 作成 / 2026-08-19 方針改訂）

GAS のコードを `docs/gas-patches/*.final.txt` の手動コピペで反映する運用に対し、
Google 公式 CLI の `clasp` を導入するための手順書。

**方針: 段階的に導入する。第1段階は「読み取り専用（pull のみ）」で、
コードの反映は従来どおり手動コピペを続ける。**
push / deploy の自動化は第2段階以降の課題とし、当面は採用しない（§1）。

---

## 0. 最重要：本番を汚染しないための前提

### 0-1. `clasp push` はリモートの状態を一切チェックしない

git と違い、`clasp push` には**コンフリクト検出もマージも「ローカルが古い」警告も無い**。
問答無用で GAS プロジェクトのファイルを上書きする。

したがって次の事故が起こりうる。**どちらも起きたことに気づけない。**

| シナリオ | 内容 |
|---|---|
| lost update | 誰かが GAS エディタを直接編集 → こちらが古いローカルのまま push → その編集が消える |
| 誤プロジェクトへの push | 別プロジェクトのディレクトリで実行 → 無関係な GAS を上書きする |

**GAS のバージョン履歴は「明示的に作成したバージョン」しか残らない。**
バージョン化されていない編集は、上書きされると復元できない。

### 0-2. ただし push だけでは本番は変わらない（確認済み）

`js/config.js` の `API_BASE_URL` は `/exec` で終わっている＝**バージョン固定のデプロイ**。

| URL 形式 | 配信されるコード |
|---|---|
| `/exec`（**本番はこちら**） | デプロイした時点のバージョンで固定 |
| `/dev` | 常に最新の HEAD（push が即反映される） |

`clasp push` が書き換えるのは HEAD だけなので、**push しても `/exec` の挙動は変わらない。**

本番が変わる経路は次の3つに限られる。

1. 明示的にデプロイした場合（GASエディタの「新バージョン」または `clasp deploy -i`）
2. `appsscript.json` を push して、スコープや実行ユーザー設定が変わった場合
3. 本番URLを `/dev` に変えてしまった場合

**→ したがって「デプロイを手動のまま残す」限り、本番汚染リスクは現行運用と変わらない。**

### 0-3. 正を2つ作らない

`docs/gas-patches/*.final.txt` と `gas/` の**両方が「正」に見える期間を作らない**。
どちらを直せばよいか分からなくなり、片方だけ直した状態で反映すると
もう片方の修正が静かに巻き戻る。

| フェーズ | 正（唯一の真実） | clone の置き場 |
|---|---|---|
| 現在 | `docs/gas-patches/*.final.txt` | 無し |
| **第1段階（§3）** | `docs/gas-patches/*.final.txt` | `gas-verify/`（**git管理外**） |
| 第2段階（§6・未定） | `gas/` | `gas/`（追跡） |

`gas-verify/` は `.gitignore` 済み。第1段階の間はリポジトリ内に二重ソースが生まれない。

## 1. 段階的導入の方針（2026-08-19 決定）

### 第1段階：読み取り専用（まずここだけやる）

- `clasp pull` して `.final.txt` と差分を取る
- **コードの反映は従来どおり GAS エディタへ手動コピペ**
- `clasp push` は**使わない**

**本番汚染リスクはゼロ。** 読むだけなので、GAS には一切書き込まない。
それでいて「今の GAS が本当に `.final.txt` と一致しているか」という
長年の不確実性（CLAUDE.md §5 の負債）は解消できる。

clasp の価値の大半はここにある。**まずこれだけで運用し、必要性を感じてから次へ進む。**

### 第2段階：push の自動化（当面採用しない）

第1段階の運用に慣れ、かつ手動コピペの手間が実際に問題になった時点で検討する。
採用する場合は §5 のガードレールを**先に**用意すること。

### 第3段階：deploy の自動化（採用しない）

`clasp deploy -i <デプロイID>` は **§0-2 の安全装置を外すコマンド**。
本番に直接触れる唯一の操作を自動化することになる。

「開発者不在での運用」（CLAUDE.md §1）の観点では魅力的だが、
**本番汚染リスクと引き換えになるため、現時点では採用しない。**
デプロイは GAS エディタでの手動操作のまま残し、人間の判断を挟む。

## 2. 導入

```bash
npm install -g @google/clasp
```

権限エラーが出る場合は、npm のグローバル install 先をホーム配下に変更するか、
以降のコマンドを `npx @google/clasp ...` に読み替える。

```bash
clasp login
```

**対象プロジェクトの所有者アカウントでログインすること。**
別アカウントだと clone が失敗するか、別プロジェクトを掴む。

> ⚠ 複数の Google アカウント／複数プロジェクトを並行して扱っている場合は、
> **どのアカウントでログインしているかを常に意識すること。**
> 認証はマシン単位で共有されるため、他プロジェクトの作業に影響しうる。

## 3. 第1段階：差分検証（ここが本命）

### 3-1. 使い捨てディレクトリへ clone

```bash
mkdir -p gas-verify && cd gas-verify && clasp clone <スクリプトID>
```

`gas-verify/` は `.gitignore` 済み。ここに落ちたものはコミットされない。

### 3-2. 現行の `.final.txt` と差分を取る

clasp はファイルをローカルへ落とす際、既定で拡張子が `.js` になることがある
（`.clasp.json` の `fileExtension` 設定に依存する）。
**実際に落ちたファイル名を確認してからコマンドを組むこと。** 以下は `.gs` の場合の例。

```bash
diff gas-verify/api.gs docs/gas-patches/api.gs.final.txt
```

```bash
diff gas-verify/admin.gs docs/gas-patches/admin.gs.final.txt
```

### 3-3. 差分の読み方

- **差分ゼロ** … `.final.txt` は実体と一致していた。以後は定期的に 3-1〜3-2 を回すだけでよい。
- **差分あり** … **事故ではなく発見。** CLAUDE.md §5 が「乖離を機械的に検出する手段がない」と
  書いている、その乖離が実在したということ。どちらが正しいかを1件ずつ判断し、
  `.final.txt` 側へ取り込む。判断に迷う差分は Claude Code に渡せば分析できる。

### 3-4. `appsscript.json` の確認

clone すると `appsscript.json`（マニフェスト）も落ちてくる。
タイムゾーン・OAuth スコープ・Web アプリの実行ユーザーやアクセス権が含まれる。

第1段階では読むだけなので影響しないが、**第2段階へ進む場合はこのファイルが
push 対象に含まれ、現在のデプロイ設定を上書きしうる**点に注意（§0-2 の経路2）。

### 3-5. 運用に組み込む

GAS を手動更新した後（＝再デプロイした後）に 3-1〜3-2 を実行し、
差分ゼロを確認する。これを習慣にすれば、乖離は発生した時点で検出できる。

---

## 4. 第1段階でやってはいけないこと

- **`clasp push` を実行しない。** 第1段階に push は不要。
  誤って実行すると §0-1 の事故が起きる。
- **`gas/` をリポジトリに作らない。** 正が2つになる（§0-3）。
- **`.clasp.json` / `.clasprc.json` をコミットしない。**
  `.clasprc.json` は OAuth リフレッシュトークンを含む。漏洩すると GAS を操作される。
  （`.gitignore` 対応済み・2026-08-17）

## 5. 第2段階へ進む場合に先に用意するガードレール

push を使い始める前に、以下を**必ず**揃えること。順に効果が高い。

### 5-1. push 前に必ず版を切る（最も効く保険）

```bash
clasp version "push前のバックアップ"
```

復元ポイントができる。何を上書きしても、このバージョンに戻せる。

### 5-2. pull で差分が出たら push を中断する

「気をつける」は必ず破綻するので、機械的に止める。
pull → 差分あり → 中断、という手順をスクリプト化して、それ以外の経路で push しない。

差分が出たということは、**誰かが GAS エディタを直接編集した**ということ。
その内容を取り込むまで push してはいけない。

### 5-3. 実行前に対象プロジェクトを確認する

どの GAS に対して操作しようとしているかを push 直前に必ず表示・確認する。
複数プロジェクトを並行して扱う環境では、ディレクトリ間違いによる誤 push が現実的なリスク。

### 5-4. 稼働中イベントの期間中は実施しない

CLAUDE.md §2 のとおり。デプロイは数秒の断を伴う。

## 6. 第2段階へ進む場合の切り替え手順（未実施）

1. `gas/` をリポジトリに作り、検証済みのコードと `appsscript.json` を配置する
2. `.clasp.json` の `rootDir` を `gas/` に向ける（`.clasp.json` 自体はコミットしない）
3. **`docs/gas-patches/*.final.txt` を削除する**（正を1つにする。履歴は git に残る）
4. CLAUDE.md を §7 のとおり書き換える
5. `docs/CHANGELOG.md` に移行を記録する

3 と 4 は**同じコミットで行う**。片方だけ入ると、正が2つある期間ができる。

## 7. 第2段階へ進んだ場合の CLAUDE.md 改訂（草案・未適用）

### §2 の扱い

> - **`docs/gas-patches/*.final.txt` を変更したら「GAS 再デプロイ必須」と明示的にユーザーへ伝える。**

`gas/` の変更に読み替える。**デプロイは手動のままなので、このルール自体は残す。**

> - **`docs/gas-patches/*.final.txt` を変更するPRは、常に1つずつ完結させる**

**維持する。** push とデプロイが分離している以上、
「複数のGAS修正PRを未マージのまま並行して抱えない」という制約は変わらない。

### §3 の全面書き換え

「リポジトリに `.gs` が含まれていない」という前提が消える。
`gas/` が実体と同期していること、同期手段が clasp であることを書く。

### §5 の技術的負債

> - **GAS 側とリポジトリの乖離を機械的に検出する手段がない。**

**第1段階の時点で解消できる。** `clasp pull` + `diff` で機械的に検出できるため、
第2段階へ進まなくてもこの項目は更新してよい。

## 8. 既知のつまずき（実例）

1. **`clasp push` だけでは公開中の Web アプリは更新されない。**
   push は GAS エディタ上のファイルを書き換えるだけ。反映には「デプロイを管理」から
   新しいバージョンとして更新する操作が別途必要（＝§0-2 の安全装置）。
2. **デプロイ設定（実行ユーザー等）を変更すると、バージョン選択が古いものに戻ることがある。**
   その状態で保存すると、直前に push したファイルが「見つかりません」というエラーになる。
   設定変更時は必ずバージョンが「新バージョン」になっているか確認する。
3. **新しいサービスを使い始めると、既存の OAuth 認可にスコープが含まれず再認可が必要になる。**
   Web アプリ URL を直接開き直して認可し直す。
4. **`clasp deploy` で `-i <デプロイID>` を省くと新規デプロイになり、API URL が変わる。**
   URL が変わると `js/config.js` の `API_BASE_URL` を書き換えるまで全機能が停止する
   （USER_MANUAL.txt にも同じ警告がある）。第3段階を採用しない理由のひとつ。

## 9. ロールバック

### 第1段階をやめる場合

`gas-verify/` を削除するだけ。リポジトリも GAS も無変更なので、失うものは無い。

### 本番のコードを戻したい場合

GAS はデプロイのバージョン履歴を保持している。
「デプロイを管理」から**以前のバージョンを選び直すだけ**で戻せる。
API URL も変わらず、コードを貼り直す必要もない。

**ただしこれは「バージョンとして保存済みのもの」に限る。**
バージョン化されていない HEAD の編集は、上書きされると復元できない（§0-1）。
