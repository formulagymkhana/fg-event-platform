# 変更記録（CHANGELOG）

**このファイルの目的は「GAS 再デプロイの要否」と「現在デプロイ済みの GAS バージョン」の記録です。**

GAS はリポジトリ管理外のため、push しても自動反映されません。
再デプロイの履歴が追えなくなると、`docs/gas-patches/*.final.txt` と
実際に GAS 上で動いているコードの乖離が検出不能になります。
それを防ぐことがこのファイルの存在価値です。

## 運用ルール

- **コミット毎ではなく、機能単位で追記する。**細かい修正まで書かなくてよい
  （それは `git log` の役割）。
- **GAS 再デプロイを伴う変更は必ず記録する。**フロントのみの変更は任意。
- 新しいエントリは**先頭（上）**に追記する。

各エントリの形式：

```
## YYYY-MM-DD 変更内容の要約
- 変更ファイル: （箇条書き）
- 変更内容: （何をどう変えたか）
- 理由/背景: （なぜ）
- GAS: 再デプロイ必須 / 不要
- 申し送り/注意点: （あれば。なければ「なし」）
```

> 2026-06-30〜07-29 の期間は「コミット毎に追記」という旧ルールが守られず、
> 72 コミットが未記録のまま蓄積しました。ルールを実行可能な粒度に緩和した経緯は

- 変更ファイル: `docs/gas-patches/api.gs.final.txt`, `js/admin.js`, `js/api.js`,

  - GAS に `resolveCompanyViewEvent_` / `companyViewEvent_` を新設。
    `resolveViewKey` / `getCompanyView` / `getCompanyStampVisitors` の3アクションで、
    `event` が渡されなければサーバー側が**「開始済みの最新イベント」**を解決する。
    `event` が明示されていればそれを優先する（配布済みURLとの後方互換）。
  - `js/api.js` の `EVENT_OPTIONAL_ACTIONS` に上記3アクションを追加。
    クライアント側の当日判定を通すと、会期翌日から `no_active_event` で
    打ち切られ、**会期後に一覧を見るという主用途が死ぬ**ため。
  - `docs/USER_MANUAL.txt` に企業QRが使い回せる旨と判定ルールを追記。
- 理由/背景: 企業へ配る閲覧QRはラミネート加工して毎年使い回す想定だった
  （2026-08-19 ユーザーより要件確認）。従来はURLにイベントIDが入っていたため、
  イベントごとに作り直して配り直す必要があった。
- **解決ルール**: 「開始日 <= 今日」の公開中イベントのうち、開始日が最も新しいもの。
  - 会期中 → そのイベント
  - イベント間 → 直前に開催したイベント（引き続き閲覧可）
  - 次イベント開始日 → その日から自動的に切り替わる
  つまり「次のイベント開始日の前日までが前イベントの閲覧期限」となり、
  開催間隔が短くても期限設定を手で調整する必要がない。
- GAS: **再デプロイ必須（未実施）**
- 申し送り/注意点:
  - **`getCurrentEvent` とはルールが違う。** あちらは「今日が開催期間内」で、
    当日参加登録やスタンプ取得（会期中しか行われない）はそれで正しい。
    企業閲覧は会期後が主用途なので別ルールが必要。流用しないこと。

## 2026-08-05 P0級データ不整合3件の修正（確定順序反転・事前登録の分裂・学生編集のイベント越え）

- 変更ファイル: `docs/gas-patches/api.gs.final.txt`, `js/admin.js`, `app/admin.html`

    属性は自由入力のため、未知の値は`unknown_category`で拒否し、静かに`V`へ落とさないようにした
- 理由/背景: 稼働中イベント`2026_rd2`の受付期間中に発覚。放置すると学生IDの重複・
  申込データの分裂・別人データの汚染が本番で発生する
