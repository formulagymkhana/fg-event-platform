## [一部解決] 未登録大学の確定フロー(`actionAdminConfirmUniversity_`)に大学統合と同種の脆弱性（2026-08-04 記録・同日設計確定・2026-08-05 実装）

> **実装済み（2026-08-05、PR2）**: 下記の修正設計通りに`actionAdminConfirmUniversity_`を
> 全面改修済み。**「一部解決」としているのは、実データでの書き込み検証がまだのため**
> （大学統合機能と同様の理由。GAS再デプロイ後、初回の実運用が事実上の初検証を兼ねる）。
> また、この対応中に新たに判明した「`applyUniMergeToSheet_`（大学統合機能側）が
> シート全列を上書きするリスク」は別項目として残っている（本ファイル内、別見出し参照）。

- 状況: 大学統合機能（`actionAdminMergeUniversity_`）の4回にわたる外部レビューで、
  ロック無し・並行実行時のID/コード衝突・QR閲覧ログやwomenPairings未対応・
  セル単位更新によるタイムアウトしやすさ、といった欠陥を修正した。
  同じ`docs/gas-patches/api.gs.final.txt`内の`actionAdminConfirmUniversity_`
  （承認待ち大学に新規の確定コードを発行するだけの、統合とは別の機能）は、
  当初**今回のハードニングを一切受けておらず、同種の脆弱性を抱えたまま**だった。
- **2026-08-04時点で修正設計は確定済み（未実装）**。要点:
  - 新規シート「大学確定履歴」（`operationId, 大学名, oldCode, newCode, eventId, 状態, 更新時刻`）を
    親行(`eventId='__operation__'`)・子行(イベント単位)の2階層で持つ。親行の完了判定を
    「今その時点のアクティブイベント一覧」に依存させないことで、後日イベントが増えても
    完了済み操作が未完了扱いに戻らないようにする
  - `findActiveConfirmOperation_(name)`は大学マスターの状態に関係なく**必ず最初に**呼び、
    履歴があれば新規採番せずそれを使う（履歴保存後・マスター更新前の失敗からの再開不能を防ぐ）
  - コード採番時、他大学の未完了操作が予約済みの`newCode`も使用済み扱いにする
    （履歴保存後にクラッシュしてロックだけ解放された場合の孤立予約コードとの衝突を防ぐ）
  - ロックは統合機能と同じくスイープ完了までグローバルスクリプトロックを保持する方針を採用
    （学生登録`actionRegisterPreStudent_`と同じ`LockService.getScriptLock()`を共有しているため、
    スイープ中の登録は自然にブロックされ、途中登録によるID衝突を防げる。統合機能で既に
    受容済みの「学生登録が待たされる」トレードオフをそのまま踏襲する判断とした。
    登録エンドポイント側への新規変更は行わない）
  - `rewriteStudentUniCodeInSheet_`はシート全体ではなく`studentId`列のデータ範囲のみを
    読み書きする（既存の`applyUniMergeToSheet_`が`getDataRange()`で全列を対象にしているのは、
    もし対象シートに事務局が手動追加した数式列があれば静的値に上書きされるリスクがあると
    判明したため、新規実装では踏襲しない。**既存の統合機能側にも同じリスクが残っている**ことは
    別途申し送り、下記の別項目参照）
- 案: 大学統合で確立した「大学統合履歴」型の再開可能エンジンの設計思想を踏襲しつつ、
  確定フローは対応表(idMap)が不要な単純なコード置換である分、統合機能そのものより
  軽量な実装で足りる。PR2として別途実装予定。

## [未解決] `applyUniMergeToSheet_`（大学統合機能）がシート全列を`setValues()`で上書きする（2026-08-04 記録）
- 状況: 未登録大学の確定フロー再開可能化の設計中に判明。`applyUniMergeToSheet_`
  （`api.gs.final.txt:1948`）は対象シートを`sheet.getDataRange()`で**全列**読み込み、
  `range.setValues(data)`で**全列**書き戻している。`getValues()`は数式ではなく計算結果の
  値を返すため、もし対象6シート（`STUDENTS`/`STAMP_LOG`/`STAMP_PARTICIPANTS`/`PRIZE_LOG`/
  `PRE_REG`/`VIEW_LOG`のいずれか）に事務局が手動で追加した数式列（集計・メモ等）が
  存在した場合、大学統合の実行によってその数式が静的な値に置き換わり消える。
- 懸念/論点: 実際にそのような手動列が本番シートに存在するかはリポジトリからは確認不能
  （GASスプレッドシートはリポジトリ管理外）。大学統合機能は既にGAS本番へ反映済みのため、
  この状態のまま統合を実行するとデータが消える可能性がある。
- 案: `applyUniMergeToSheet_`も`studentId`列・`大学名`列など、実際に書き換える列の
  データ範囲だけを対象にするよう改修する（確定フロー用に新規実装する
  `rewriteStudentUniCodeInSheet_`と同じ方針）。優先度は「大学統合を次に実行する前」。
- 緩和策（実装まで）: 大学統合を実行する前に、対象イベントの該当6シートに
  手動追加した数式・チェックボックス以外の列が無いか目視確認する。

## [記録] QR閲覧ログの自動記録/手動登録の区別方法と重複抑制（2026-06-11 記録）
- 状況: 企業QR(cookie方式)による閲覧ログ自動記録を実装（card.html?viewkey=<viewKey>）。
- **区別方法**: VIEW_LOG の6列目 `source` で区別する。
  - `company_auto` … 企業cookie(viewKey)による自動記録。companyId列には GAS が viewKey から解決した企業IDが入る。
  - `manual_email` … 従来のメール手動登録。companyId列は従来通り `'manual'`。
  - 旧データ（source列なし・5列）は manual 扱い相当。getCompanyView は companyId 一致で
    フィルタするため、`'manual'` 行が企業リストに混ざることはない（従来から同じ構造）。
- **重複抑制（軽量実装）**: `company_auto` のみ、同一イベント×同一学生×同一企業の既存行が
  あれば時刻のみ更新して行を増やさない（VIEW_LOG全行を線形走査。イベント規模では問題ない）。
  `manual_email` は従来通り毎回 append（メールアドレスを変えて再登録する可能性があるため）。
- **cookie 設計**: `fg_company_view` に viewKey のみ保存（60日・SameSite=Lax）。企業IDは
  毎回 GAS 側で解決するため、クライアントから企業IDを直接信用しない。企業名表示用に
  localStorage `fg_company_name` を併用（個人情報ではないため許容）。
- 既存シートへの申し送り: 既存イベントの QR閲覧ログ シートに6列目ヘッダー `source` を
  手動で追記推奨（なくても appendRow は6列目に書き込むため動作には支障なし）。

## [解決] card.html の inline onclick が CSP でブロックされていた（2026-06-11 記録）
- 状況: card.html は CSP `script-src 'self'`（unsafe-inline なし）なのに、
  `onclick="copyEmail()"` 等の inline ハンドラを使用していた。inline イベントハンドラは
  この CSP でブロックされるため、メールコピー・一覧コピー・アコーディオン・メール登録の
  各ボタンが**本番で動作していなかった可能性が高い**。
- 結論: 企業QR実装と同時に全て addEventListener 方式へ変更して解消。
  他ページ（progress/exchange/start等）は元から addEventListener 方式で問題なし。
