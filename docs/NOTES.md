このファイルは「気になること＝後で相談したい論点」を書き溜める場所です。
作業中に気づいた懸念・改善案・後で問題になりそうな点を、その場で直さず記録して申し送ります。

各項目の形式：

```
## [未解決] 論点タイトル（YYYY-MM-DD 記録）
- 状況:
- 懸念/論点:
- 案（あれば）:
```

解決したら `[未解決]` を `[解決]` に変え、結論を1行追記します。

## [確定] 大会終了後の「公開停止」は閲覧期限に関わらず全停止（2026-08-20 ユーザー確認）
- 状況: 企業の学生一覧閲覧はイベントIDを持たない永続URLで、GAS の
  `resolveCompanyViewEvent_` が「開始済みの最新イベント（公開中のみ）」を解決する。
  そのため大会終了後にイベントを「公開停止」にすると、閲覧期限（終了日+2ヶ月 /
  `publicDeadline`）が残っていても企業は即座に見られなくなる。
- 判断: **これは仕様。** 公開停止は全機能を止めるスイッチであり、
  企業閲覧だけ例外にはしない（2026-08-20 ユーザー確認）。
- 申し送り: したがって「終了後すぐ公開停止にする」運用と
  「終了後2ヶ月は閲覧可」という案内は両立しない。
  企業に閲覧させたい期間は公開中のままにすること。
  `resolveCompanyViewEvent_` を公開停止も拾うように変えてはいけない。

## [未解決] GASコード同期に clasp を導入する（2026-08-17 記録 / 2026-08-19 方針改訂）
- 状況: GAS はリポジトリ管理外で、`docs/gas-patches/*.final.txt` を GAS エディタへ
  手でコピペして反映している。実体と `.final.txt` が一致している保証が無い
  （CLAUDE.md §5 が「乖離を機械的に検出する手段がない」と明記している負債そのもの）。
- **方針（2026-08-19 ユーザー判断）: 段階的に導入し、第1段階は「読み取り専用」に限定する。**
  `clasp pull` で差分を取るだけで、コードの反映は従来どおり手動コピペを続ける。
  push / deploy の自動化は当面採用しない。
- 理由: **`clasp push` は git と違いリモートの状態を一切チェックせず、無条件で上書きする。**
  コンフリクト検出も「ローカルが古い」警告も無い。誰かが GAS エディタを直接編集していた場合、
  古いローカルのまま push するとその編集が消え、しかも気づけない。
  GAS のバージョン履歴は明示的に作成したバージョンしか残らないため、復元もできない。
  複数プロジェクトを並行して扱う環境では、ディレクトリ違いによる誤 push も現実的なリスク。
- 確認済みの安全性: 本番の `API_BASE_URL` は `/exec`（バージョン固定のデプロイ）。
  `clasp push` が書き換えるのは HEAD だけなので、**push しても本番の挙動は変わらない**。
  本番が変わるのは ①明示的なデプロイ ②`appsscript.json` の push ③URLを `/dev` に変更、の3経路のみ。
  **デプロイを手動のまま残す限り、本番汚染リスクは現行運用と変わらない。**
- 第1段階の価値: 本番汚染リスクゼロのまま、「今の GAS が本当に `.final.txt` と一致しているか」
  という長年の不確実性だけを解消できる。clasp の価値の大半はここにある。
- 成果物: `docs/GAS_CLASP_MIGRATION.md`（全手順・ガードレール・ロールバック）、
  `tools/gas-diff-check.sh`（差分検出スクリプト。**読み取り専用。書き込み系コマンドを含まない**）、
  `.gitignore` に `.clasp.json` / `.clasprc.json` / `gas-verify/` を追加。
- 残作業: `clasp login` は対話的OAuthのためClaude Codeからは実行不可。導入と初回実行は
  ユーザーの手元で行う。差分が出た場合は内容を渡せば分析可能。
- 注意: clasp の認証はマシン単位で共有される。**他プロジェクトを別セッションで
  並行作業している場合、アカウント切替がそちらに影響しうる**（2026-08-19 に実際に
  `gh` の認証で同種の問題が発生し、切替を見送った）。

## [解決] 送り状システム向けCSVは Shift_JIS で出す（2026-08-17 記録・同日解決）
- 状況: 企業パス発送CSV（西濃運輸・`downloadEntryShippingCsv_`）を送り状発行システムへ
  そのままアップロードすると「読み込めません」となり、取り込めても文字化けした。
  値をExcelへ貼り直して新規CSVとして保存すると通っていた
  （＝Excelが保存時に Shift_JIS へ変換していた）。
- 原因: `downloadCsv_` は全CSVを **UTF-8 + BOM** で出力する。Excelでの文字化けを防ぐ
  ためのBOMだが、Shift_JIS前提の送り状システムには読めない。
- 結論（2026-08-17 解決）: 西濃向けCSVのみ `downloadCsvSjis_` で **Shift_JIS・BOM無し**
  で出力する。**外部ライブラリは追加していない。** ブラウザの `TextEncoder` は
  UTF-8専用だが、`TextDecoder('shift_jis')` は使えるため、全バイト組み合わせを
  一度デコードして逆引き表（約9,400文字）を実行時に構築している。
  変換できない文字（絵文字等）は `?` になるので、該当文字を列挙して警告する。
- 申し送り: **他のCSVは UTF-8+BOM のまま**（Excel/Numbersで開く運用のため変えてはいけない）。
  出場校パス発送CSV（ゆうパック）は印刷ツール未確定のため据え置き。
  ツールが決まった際、Shift_JIS が必要なら `downloadCsvSjis_` に差し替えるだけでよい。

## [解決] 応援学生受付リストで「サービス作業クラス」を補欠選手登録列に出していた（2026-08-17 記録・同日解決）
- 状況: 事前登録シートの **「サービス作業クラス」列は、参加区分に関わらず
  「メカニックとしてどのクラスを担当するか」の回答**である。補欠ドライバー
  （`app/register-pre.html` の `rg-bService`）も見学・応援学生（`f-s-serviceclass`）も、
  同じ意味の設問に答えている。にもかかわらず `buildSupportRows_`（`js/admin.js`）は
  この1列を参加区分で振り分け、補欠の回答を**「補欠選手登録」列**に出していた。
  その結果、受付リストの補欠選手登録欄に「FGクラス」「FG/女子クラス」
  「サービス作業は実施しない/来場予定はない」といった、その列の意味と無関係な値が並んでいた。
- 懸念/論点: **列名とデータの意味が対応していない（ラベリングの取り違え）**。
  補欠かどうかは「参加区分」列だけで決まるため、補欠選手登録列にクラスを出す理由はない。
  運用上も、補欠選手は登録の前日までに申請・許可された者に限られ、当日の交代は原則不可。
  保険は補欠は主催側が加入、見学のメカニックは自己加入で証明書提出が必要、という違いがある
  （＝この2者を同じ扱いにしてはいけない）。
- 結論（2026-08-17 解決）: 補欠選手登録列は参加区分だけを見て「あり」を表示し、
  クラス情報はメカニック登録列に集約した（補欠・見学応援で共通）。
  補欠が「実施しない」を選んだ場合のみメカニック列に「実施なし」と明示し、
  見学応援は従来通り空欄。未回答（空欄）は「実施なし」と断定せず空欄のままにしている。
  保険証明チェック（`needDoc`）は**変更していない**（補欠は対象外のまま）。
  あわせてフォーム側の表記ゆれを統一（`FG/女子クラス`→`FGクラス/女子クラス`、
  `サービス作業は実施しない/来場予定はない`→`実施しない`）。旧データは
  `includes('実施しない')` 判定と `normalizeServiceClass_` の表示正規化で吸収しており、
  **シートの書き換え（データ移行）は行っていない**。GAS再デプロイ不要。

## [解決] 大学確定・統合の実行中に学生登録が落ちると、学生には `server_error` としか出ない（2026-08-10 記録・同日解決）
- 状況: 大学確定(`actionAdminConfirmUniversity_`)・統合(`actionAdminMergeUniversity_`)は
  全イベントのスイープ完了までスクリプトロックを保持する。これは
  「スイープ中の新規登録をブロックしてID衝突を防ぐ」ための**意図的な設計**で、
  `api.gs.final.txt` のコメント（`actionAdminConfirmUniversity_` の直上）にも
  受容済みのトレードオフとして明記されている。ここまでは仕様どおり。
- 懸念/論点: **問題はロックそのものではなく、待ちきれなかったときの見え方。**
  学生登録側の `actionRegisterWalkIn_` / `actionRegisterPreStudent_` は
  `lock.waitLock(15000)` を **try/catch なしで**呼んでいる。15秒で取得できないと
  例外が飛び、`dispatch_` の catch に落ちて `err_('server_error')` になる。
  同じファイル内の他のロック取得箇所（`actionSaveStamp_` 等）は
  `try { lock.waitLock(6000) } catch { return err_('lock_timeout') }` と書かれており、
  ここだけ扱いが違う。学生には「サーバーエラー」としか出ないため、
  **少し待って再送信すれば通る状況なのに、諦めるか事務局へ問い合わせることになる。**
- 結論（2026-08-10 解決）: 登録2関数＋`actionExchangePrize_` のロック取得を
  `try/catch` + `err_('lock_timeout')` に統一し、これで `api.gs.final.txt` 内の
  ロック取得6箇所すべてが同じ形になった。あわせて、調査中に判明した
  **`lock_timeout` が `err_()` の MSG マップに存在せず、生の文字列 `lock_timeout` が
  そのまま利用者に表示されていた**問題も修正（`stamp.js` / `progress.js` /
  `exchange.js` は `res.message` を直接表示するため実際に露出していた）。
  フロントは `register.js` / `register-pre.js` に再試行を促す専用文言を追加。
  **GAS再デプロイ必須（CHANGELOG 2026-08-10 参照）。**

## [未解決] CSV出力が5系統に散らばっており、うち3つは今もインラインでBlobを組んでいる（2026-08-10 記録）
- 状況: `js/admin.js` のCSV出力は、共通ヘルパー `downloadCsv_` を通る経路と、
  関数内で直接 `new Blob(...)` を組む経路が混在している。後者は
  QRパス（`downloadPassQrCsv_` 付近）・宿泊リスト（`downloadHotelListCsv_`）・
  出展申込（`downloadEntryCsv_`）の3つ。いずれも `'﻿' + csv` を各自で付けている。
- 懸念/論点: 2026-08-10 に発覚した `downloadCsv_` の二重定義（引数順が逆で、後の定義が
  前を上書きし、3つのCSVがファイル名と中身が入れ替わったまま気づかれなかった）は、
  この「同じことを各所でやる」構造が温床になっている。BOM付与・改行コード・
  クォート規則が各所に散ると、次に同種の事故が起きても静かに壊れる。
- 案: 3つのインライン実装を `downloadCsv_(filename, body)` へ寄せる。
  ただし今回は「動いている経路には触れない」方針で見送った（自動テストが無く、
  1つずつ手で確認するコストが高いため）。発送業務の繁忙期を外して着手したい。

## [受容] 仮コードの再利用と「非アクティブイベント除外」が組み合わさると、終了済みイベントのstudentIdが別大学を指しうる（2026-08-05 記録・同日受容）
- 状況: `loadUniversityMaster_`（`admin.gs.final.txt:350`付近）の`maxAutoCode`は
  **状態が`自動割当(要確認)`の行だけ**から算出している。したがって大学を「確定」すると

  意図的に対象外とするため、終了済みイベントには旧仮コードのままのstudentIdが残る。
  この2つが重なると、終了済みイベントのstudentIdのコード部が、後から別の大学に
  割り当てられた仮コードと一致してしまう。

## [解決] `applyUniMergeToSheet_`（大学統合機能）がシート全列を`setValues()`で上書きする（2026-08-04 記録・2026-08-05 解決）

> **解決済み（2026-08-05）**: `studentId`列・`大学名`列だけを個別に読み書きするよう変更し、
> 手動追加された数式列に書き戻さないようにした。モック環境で、数式を入れた列が
> 統合後も保持されることを実行確認済み。以下は当時の記録。

- 状況: 未登録大学の確定フロー再開可能化の設計中に判明。`applyUniMergeToSheet_`
  （`api.gs.final.txt:1948`）は対象シートを`sheet.getDataRange()`で**全列**読み込み、
  `range.setValues(data)`で**全列**書き戻している。`getValues()`は数式ではなく計算結果の
  値を返すため、もし対象6シート（`STUDENTS`/`STAMP_LOG`/`STAMP_PARTICIPANTS`/`PRIZE_LOG`/
  `PRE_REG`/`VIEW_LOG`のいずれか）に事務局が手動で追加した数式列（集計・メモ等）が

  （GASスプレッドシートはリポジトリ管理外）。大学統合機能は既にGAS本番へ反映済みのため、
  この状態のまま統合を実行するとデータが消える可能性がある。
- 案: `applyUniMergeToSheet_`も`studentId`列・`大学名`列など、実際に書き換える列の
  データ範囲だけを対象にするよう改修する（確定フロー用に新規実装する
  `rewriteStudentUniCodeInSheet_`と同じ方針）。優先度は「大学統合を次に実行する前」。
- 緩和策（実装まで）: 大学統合を実行する前に、対象イベントの該当6シートに
  手動追加した数式・チェックボックス以外の列が無いか目視確認する。
